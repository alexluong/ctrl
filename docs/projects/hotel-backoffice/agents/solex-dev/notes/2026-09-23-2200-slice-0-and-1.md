## The one class of bug that kept recurring

Three separate findings, all the same shape, and worth naming because it will
keep happening:

**If a command's guard reads a table another command writes, both sides have to
serialise on the same guard — not just the writer.**

- `takeOutOfOrder` didn't version availability → a room could be withdrawn in
  the same instant it was being sold, both writes succeeding, neither side
  wrong from its own point of view.
- `checkIn` read the rooms row for serviceability but didn't version
  availability → interleave with a withdrawal puts a guest in an out-of-order
  room. Architect caught this one (B3) *after* I'd "closed" the first.
- `recordChange` retried with a precomputed decision → two desks both pass the
  "not already out of order" check, the loser retries blindly and overwrites.

All three look correct in isolation. None is visible in a unit test. Each one
needed either an integration test driving the interleave, or someone reading
the code asking "what else touches that table?".

Architect now has it as a checklist line. I'd go further: **the guard is not
about the table being written, it's about the fact being read.**

## Decisions I made and would defend

**`SOLEX_DEV_USER` is a build-time boundary, not a runtime flag.** The lookup
lives in `runtime/node.ts`; `runtime/cloudflare.ts` returns `undefined`
unconditionally, so the deployed Worker contains no environment read to enable.
Verified against a real build — no `process.env.SOLEX_DEV_USER` in `dist`, and
node.ts's NODE_ENV guard absent from the server bundle, which is how you can
tell the stub is linked. This is deliberately unlike `SYSTEM_CONSOLE_FALLBACK`,
which I deleted the same day for being a dev/prod difference on an
access-control path. That was a branch inside shipped code; this is not in the
shipped code at all.

**Hand-wrote the D-12 migration.** drizzle-kit emitted `ADD COLUMN … NOT NULL`
with no default, which SQLite refuses on a populated table — so it silently
depended on a staging wipe that hadn't happened. Rebuilt and backfilled
instead. "Works because the table is empty" is now a checklist line too.

**Disable a control only for a no-op, never for a rule.** Architect reported
"clicking mark-clean on an OOO room does nothing". The error renderer existed;
the button was disabled. So the UI was enforcing a domain rule by hiding the
control, meaning the rule lived in two places and only one could explain
itself. Now the click goes through and the domain refuses it out loud.

**Projector registry excludes contacts and guests.** Rebuilding them from the
log would resurrect personal data somebody asked to have erased. "Rebuild
everything" is the obvious instinct and it's wrong here. Architect wrote it
into D-20.

**Declined architect's `WHERE version = :seen` row guard.** In a batch, an
UPDATE matching zero rows still commits — so the event lands with no row
change, converting a lost update into silent log/table divergence. Worse than
the race. The stream's UNIQUE(stream, version) already rolls the whole batch
back. They agreed.
