## Things worth remembering

**The paid-plan question was not incidental.** Better Auth hashes with pure-JS
scrypt, ~80ms CPU. Workers free tier allows 10ms per request, so on free this
does not work at all — sign-in fails outright, not slowly. We are on paid (30s),
so the default stands. Escape hatch if that ever changes: custom `hash`/`verify`
using `node:crypto.scryptSync`, `nodejs_compat` is already on. Upstream issues
better-auth#8860 and #8456. I checked this *before* recommending the library,
which was the right order — it would have been an expensive thing to discover
after building.

**I hand-wrote the Drizzle schema rather than running their CLI generator.**
Their CLI wants to load the auth config, and ours resolves through Vite aliases
that node does not. Hand-writing also let it read like the rest of `schema.ts`.
The risk that buys is drifting from what the library expects, so `auth.test.ts`
signs a real user in against a real SQLite file. That test caught nothing today
and is the whole reason I'd trust an upgrade tomorrow.

**A security bug I introduced and then found.** Adding auth put password hashes
and live session tokens in the same database as the room board — and the system
console's table browser shows any table it finds. Signing in and opening
`/system/tables/session` printed a working session token. Not a record of a
credential: the credential. Anyone with console access could have become another
user.

Found it by actually looking at the deployed console after the change rather
than reasoning about it. Fixed by redacting on **column name, not table name**,
so a future table with a `token` column is covered the day it is added rather
than the day someone remembers the list exists. `queries.test.ts` asserts the
hash and token never appear in the output at all, not merely that the cell is
redacted.

The general lesson: the table browser is a generic surface, and generic
surfaces acquire this class of bug automatically every time the schema grows.
That is now the strongest argument for dropping it in favour of Drizzle Studio
— stronger than the duplication argument I made to Alex earlier.

**Names do not belong in an append-only log.** `events.actor` stores `user:<id>`
and resolves to a display name at read time. People marry, get their spelling
corrected, and leave; a name written into a permanent log is wrong the day it
changes, and there is no honest way to fix it. The flip side: events written
before today still say `"reception"`, and I left them. Rewriting history to
flatter a new design is exactly what an event log exists to prevent.

**Deleted `SYSTEM_CONSOLE_FALLBACK`.** It made the console open on a dev machine
and locked when deployed. It was convenient and it was a dev/prod behavioural
difference sitting on an access-control path — the worst possible place for one.
Real accounts made it unnecessary.
