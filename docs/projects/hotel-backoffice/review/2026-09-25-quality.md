# SoLex code review: quality, organization, clarity (reviewer A)

Date: 2026-09-25 · solex `9b30ff9` (vi pass 3 + e2e tidy) · read-only review
Scope: module boundaries, naming, duplication and abstraction, file size and shape, comments, dead code, tests, i18n. Formatting and lint-level style are out of scope.
Gate at review time: `vitest` 517/517 green (33 files, 10 s) · `tsc --noEmit` clean · `biome ci` 4 warnings, 1 info.

## 1. Overall assessment

**Grade: B+.** The core is well built. There is one `Hotel` object whose methods are the commands, a `Store` port with a lint-enforced drizzle boundary, and one write path (`handleAcross`) with retry-by-thunk and an idempotency lookup before the rules run. Tier (a) aggregates use `fold*` + `decide`, and tier (b) items use `xRules` + a row helper, so a file's name tells you its tier. The scenario suite reads like the product spec. For a codebase built this fast, that is unusually disciplined, and the docs match the code on the big things.

The weak spots show up as the domain grew: the conventions were applied by copying code instead of being pulled into shared helpers.
- The "decide → fold accounts → append to every touched stream" write helper exists in three near-identical copies.
- Opening a ledger account is a *nested* `commit` inside another command's plan in 13 places, which breaks the stated one-batch-per-command rule.
- Screen read models (room-map state, history assembly) live in server-fn adapters, so they can't be tested through `Hotel`.
- The UI decides permissions with `role === "owner"` in 13 places instead of using capabilities.

The largest route components, `setup.tsx` and `stays.$id.tsx`, are 500–830-line single functions. Comments are plentiful (about 22% of lines) and mostly explain *why*, but some have gone stale or become changelog narration.

**What the grade hinges on:** consolidating the ledger write path, which also fixes the nested commits, and moving read models onto `Hotel`. Those two changes make the architecture true everywhere rather than mostly, and would put this at A-. None of the findings block the demo.

## 3. Findings (ranked by impact)

### F1. The ledger write helper is copy-pasted three times, and a fourth path is test-only — high
**Where:** `server/hotel/folios.ts:127-197` (`write`), `server/hotel/receivables.ts:44-93` (`write`), `server/hotel/expenses.ts:34-70` (`write`), `server/hotel/ledger.ts:49-72` (`appendEntry`) + `ledger.post/reverse/closeAccount` (`ledger.ts:120-220`).
**What:** Each copy does the same work: run `decide()`, fold every touched account, stamp `approvalId` onto the vocabulary events via `payload as object`, then append the events to every account stream at its version, plus `also` streams. They have already drifted:
- `folios` supports multi-entry writes and `closes`.
- `receivables` supports `also`/`approvalId` but only one entry.
- `expenses` supports neither.

`hotel.ledger.post`, `reverse` and `closeAccount` are called only from `ledger.test.ts`. So the ledger's own tests exercise a write path that production never uses, and the path production *does* use has no direct test of its own. `accountForMethod` (folios) and `tillFor` (expenses) are the same function under two names.
**Why it matters:** Money is the area where drift is most expensive. The next ledger-backed command, such as the cash-handover `CloseShift`, will be copy number four.
**Direction:** Build one `ledgerWrite({ decide, also, approvalId })` in `hotel/ledger.ts` that covers the superset (entries[], closes, also). Rewrite folios, receivables and expenses on top of it. Delete `post/reverse/closeAccount`, or make them thin callers of the same helper so `ledger.test.ts` tests the real path.

### F2. Opening an account is a nested commit inside another command's plan — high
**Where:** `folios.ts:112` (`ensure` → `ledger.ensureAccount` → `openAccount` → `ctx.store.commit`), called from inside `decide` at `folios.ts:348, 543, 620, 686-687, 755-756, 833, 897-898`; `expenses.ts:99-100`; `receivables.ts:135, 210`.
**What:** `plan()` is supposed to be a pure read-and-decide thunk (`store/log.ts:208-216`). Here it issues its own D1 batch (`ledger.account_opened`) before the outer batch commits, so the first charge on a folio is two batches. The nested commit also carries no `commandId`, runs again on every retry, and checks `folio.post_charge` regardless of which command triggered it. For example, an expense or receivable write-off opening `expense:writeOff` passes a *charge* capability check.
**Why it matters:** This breaks two rules the codebase is built on and documents: D-8 (ii), one intent = one batch, and the purity of `plan`. It is invisible in tests because it happens to be harmless today, since account opens are idempotent. It is exactly the kind of "looked fine in isolation" pattern `stack.md` §"The bug class this project keeps producing" warns about.
**Direction:** Have `decide` return the `ledger.account_opened` events for any account whose fold says `!exists`, and append them in the same batch (version 0 → 1). The fold already tells you which accounts are missing. This falls out naturally from F1.

### F3. `approvals.grant` decides outside the plan, against D-12 (f) — high (small fix)
**Where:** `server/hotel/approvals.ts:84-99`.
**What:** `grant` does three things before `commit` starts: it folds the approval stream, calls `approvalDecide.grant()` (which refuses `approval.notOpen`), and captures `expectedVersion`. As a result:
- A second click on Approve with the same `commandId` gets `approval.notOpen` instead of the original answer. D-12 (f) exists specifically to prevent that.
- A retry after a collision reuses a stale approval version, so it runs out of retries and the owner sees `unknown` instead of an answer.
- `if (!row) return;` runs *after* the decision.

**Direction:** Pass a thunk (`approval: () => Promise<ApprovalAppend>`) that the folio/receivable `write` resolves inside its plan. Add a scenario test: "an owner's double click on Approve applies once and answers ok twice".

### F4. Read models live in adapters, not on `Hotel` — med
**Where:** `server/api/rooms.ts:137-205` (room-map tile state machine `ooo/occdirty/in/dep/arr/vacdirty/ready`, departure logic), `api/rooms.ts:214-262` (room panel "who is in it now"), `api/booking.ts:339-406` (booking view merges and sorts histories, resolves actors, assembles routing), plus history assembly repeated in `api/{booking,people,reports,rooms,setup,users}.ts`. The occurredAt comparator is copy-pasted 3×.
**What:** D-24 says the read side is exposed on `Hotel` the same way as commands. In practice about half of `server/api` is view-model composition, and the room-map state is a product rule (§6 "derived, never stored"). `api/` has one test file, `result.test.ts`. These derivations are covered only by e2e.
**Why it matters:** "Screens as tests" stops at the command boundary. A change to what counts as a departure on the map, or the order history sorts in, has no fast test.
**Direction:** Add `hotel.views.roomMap()`, `hotel.views.booking(id)` and `hotel.history.of(ref)` (the last one returns named, sorted events and replaces the six copies of `resolveActors` + `nameActor`). The adapters shrink back to parse → call → return, and each view gets a scenario test.

### F5. The UI decides permissions by role name, not capability — med
**Where:** `routes/__root.tsx:52,123,130-134`, `stays.$id.tsx:436,454`, `bookings.$id.tsx:158`, `guests.index.tsx:56`, `expenses.tsx:47`, `receivables.tsx:56`, `setup.tsx:67`, `accounts.index.tsx:42`, `accounts.$id.tsx:33`.
**What:** The domain has explicit capability bundles (`staff/domain.ts`, `can(role, cap)`), but the screens hard-code "owner can void / write off / erase / see setup". That is the role → capability table duplicated in the UI. The server still enforces, so this is not a hole, but the UI is holding a rule.
**Why it matters:** "Custom roles / editable capability bundles" is a listed follow-up (mvp.md §4). When it lands, every one of these 13 checks becomes wrong silently: a button shows up and gets refused, or an allowed action is hidden. The approvals "ask the owner" rendering also depends on this being right.
**Direction:** Have the root loader put `viewer.capabilities` (computed server-side with `can`) on the context, and use a `useCan("folio.void")` helper. Setup and accounts then use the existing `read()` → `allowed:false` shape instead of a role check.

### F6. Oversized route components, one function per page — med
**Where:** `routes/setup.tsx` (the `Setup()` function spans lines 49-881 and has 9 inline forms), `routes/stays.$id.tsx` (`Stay()` is about 500 lines), `routes/bookings.index.tsx` (`Bookings()` spans lines 74-580 with 12 `useState`), `routes/bookings.$id.tsx`.
**What:** Every form repeats the same pattern: `preventDefault` → `new FormData` → `String(form.get(...))` → `run(key, id => fn({data:{…, commandId}}))` → `say()`. That block appears 74 times across routes and ui. There are also 184 inline `style={{…}}` objects. Pages that were built out properly (`ui/folio.tsx`, `ui/settle.tsx`, `ui/master-folio.tsx`) prove the extraction works.
**Why it matters:** These are the files the UX review will change most. An 830-line function with nine forms sharing one `useCommand` and one notice is where regressions hide. The shared hook's `inFlight` complexity (`ui/command.tsx:91-98`) exists partly because one hook serves a whole page.
**Direction:** Split each Setup section into its own component with its own `useCommand` (for example `setup/RoomTypes.tsx`). Add a small `useFormCommand(key, toInput, fn)` helper that owns the FormData → run → notice sequence. Replace recurring inline styles with a handful of classes. Keep it mechanical and behavior-neutral, with e2e as the safety net.

### F7. Events are untyped strings and payloads are cast at each read — med
**Where:** 62 distinct `type: "x.y"` string literals across `server/`; about 50 `payload as {…}` casts (`store/projections.ts` 9, `stay/domain.ts` 7, `hotel/folios.ts` 7, `store/folio.ts` 5, `booking/domain.ts` 5 …). Projection rows expose enums as `string`, which forces UI re-casts (`stays.$id.tsx:80` restates `StayStatus`).
**What:** Nothing ties an event's producer to its fold, its projector, `history.tsx` and the i18n key. `i18n/codes.test.ts` works around this by regex-scanning source files for `type: "…"` and `…RuleCode` unions. That is clever and does catch drift, but it is a sign the registry is missing.
**Why it matters:** A renamed payload field compiles fine and breaks a fold or projector at runtime. D-12's upcaster rule depends on knowing a type's shape per `schemaVersion`, and today that is only by convention.
**Direction:** Add a per-context `events.ts` with a discriminated union, e.g. `StayEvent = {type:"stay.checked_in"; payload:{…}} | …`, used by `decide` (return type), `fold` (switch narrowing) and projectors. Adopt it incrementally, starting with the tier-(a) money streams. After that, `codes.test.ts` can use the types instead of regexes.

### F8. Module layout is layered and doesn't follow the bounded contexts; naming collides — med
**Where:** One context is spread across five directories. For example, folio = `server/folio/domain.ts` + `server/hotel/folios.ts` + `server/store/folio.ts` + `server/db/ledger-schema.ts` + `server/api/folio.ts` + `ui/folio.tsx`. Booking and stay projectors sit in the generic `store/projections.ts`, while folio, ledger and approvals have their own files. Schema files don't match contexts: `guests`/`contacts` are in `booking-schema.ts`; `approvals`, `expenses` and `chargeCategories` are in `ledger-schema.ts`; `hotelStaff` is in `setup-schema.ts`. Singular vs plural is mixed across layers (`api/booking.ts` vs `api/rooms.ts`, `store/expense.ts` vs `store/approvals.ts`).
**Name collision:** "account" means three things:
- the Better Auth `account` table;
- the ledger `accounts` table;
- `store.accounts` / `hotel.users` / route `/accounts`, meaning staff logins.

**Why it matters:** product.md §5 names the contexts (Setup, Reservations, Rooms, Billing, Ledger, Guests, Expenses), but the tree does not, so the next engineer has to learn a second map. The "account" overload will cause real confusion in bookkeeping code.
**Direction:** Don't restructure before the demo. Afterwards: (1) rename logins to `logins`/`users` throughout the store and routes, and keep "account" for the ledger; (2) move schema tables into files by context; (3) optionally move to `server/<context>/{domain,commands,store,api}.ts` context folders. The layered layout is defensible; the collisions are not.

### F9. Stale and orphaned comments, and changelog narration — med
**Where:**
- Orphaned or stacked doc blocks, where code was inserted between a comment and its target: `hotel/current.ts:23-28` (documents a function that isn't there), `hotel/index.ts:216-218` and `:239-240` (profile and account docs sit above the wrong members), `store/index.ts:325-326` ("Who works here" above `expenses`), `staff/domain.ts:74-75`, `setup/domain.ts:573-585`, `hotel/setup.ts:26-37`.
- Stale facts: `hotel/folios.ts:41-43` ("group bookings are not built"), `db/setup-schema.ts:27` (capacity "not yet a rule"; G35 made it one), `stay/domain.ts:323,355` ("nothing is posted in slice 1").
- About 28 comments narrate history ("there used to be three of these", "the two-commit void I had to fix", "a deliberate call I got wrong").

**What:** About 22% of source lines are comments, and most are genuinely good *why* comments tied to D-/G-/N- ids (836 references). The failure mode is rot: comments are appended to, not maintained. Some read as a diary, and the IDs are opaque without the ctrl repo.
**Why it matters:** When comments are this dense, a stale one gets believed. The orphaned JSDoc blocks show up on the wrong symbol in editor hover.
**Direction:** Do one sweep: fix the seven orphaned blocks and the stale facts, and cut narration down to the rule it justifies (the history belongs in git and ctrl). Add a line to the ctrl workflow: "when a slice lands, grep for 'not built / slice N / not yet' in touched files".

### F10. Legacy compatibility shims with no legacy data — low/med
**Where:** `rooms.room_type` + nullable `room_type_id` with `room.roomTypeId ?? room.roomType` fallbacks at `hotel/stays.ts:38,231`, `hotel/availability.ts:59`, `hotel/setup.ts:172`; slug-ids "because slice 1 wrote `double`" (`setup/domain.ts:27`, `db/setup-schema.ts:23`, `testkit/index.ts:197`).
**What:** These shims keep pre-G8 data working. Staging was wiped (D-26) and there is no production, so they protect nothing, but they add a second source of truth for a room's type and a branch in the availability code.
**Direction:** Before production: make `room_type_id` NOT NULL, drop `room_type` (render the name through a join or lookup), and delete the fallbacks. Keep slug ids if you like them, but stop justifying them by slice-1 data.

### F11. Two `CommandResult` types, one on each side of the wire — low/med
**Where:** `server/api/result.ts:21-25` vs `ui/command.tsx:26-35`.
**What:** They are hand-maintained twins with slightly different shapes: `result: T | null` vs `T`, and `code` required vs optional. Separately, adapter zod primitives are redefined per file: `const commandId = z…` appears 9× and `money` 2×. `parse`/`InputError` live in `server/booking/input.ts` but are imported by every adapter. Folio schemas are inline in `api/folio.ts`, while booking schemas live in `booking/input.ts`.
**Direction:** Have the UI import the server's `CommandResult` type. Move `parse`, `InputError` and the shared primitives into `server/api/input.ts`. Pick one home for wire schemas: inline in `api/*` is the better fit for "adapters are shape-only".

### F12. `store/index.ts` is 688 lines of triple-declared wiring — low
**Where:** `server/store/index.ts:1-688`.
**What:** Every query is written once as a function, once as an interface signature (`Awaited<ReturnType<typeof fn>>`), and once in the wiring. Every call also passes `hotelId` explicitly, even though a store is always used for one hotel. The port's types are inferred from drizzle row types, so the "port" hands drizzle-shaped rows to the domain. There are 12 `as unknown as Write` casts.
**Why it matters:** Adding a query means touching three places in one file plus the query file. The stated benefit, swappable stores, was deliberately given up (D-24 amendment: one `SqliteStore`).
**Direction:** Build a hotel-scoped store (`sqliteStore(db).forHotel(id)`) and let the interface be `typeof` the implementation object, keeping the biome import boundary as the real guard. This is not urgent. It is friction, not risk.

### F13. `Hotel` surface has redundant and inconsistent entry points — low
**Where:** `server/hotel/index.ts`:
- `people.contact/guests` (lines 171-174) duplicates `contacts`/`guests`; the comment says it was kept so screens didn't have to move.
- `bookingsOf(ctx, setup.rates, setup)` passes `setup` twice.
- 19 hand-written `events.ofX` wrappers.
- Every domain module exports `decide` and `streamIdFor` under the same names, which forces 9 import aliases here.

**Direction:** Delete `people`, collapse `events.ofX` into `history.of(ref)` (see F4), and use namespace imports (`import * as Stay from "#/server/stay/domain"`).

### F14. i18n: a single 2,100-line file with en and vi side by side — low
**Where:** `src/i18n/messages.ts` (en 15-1066, vi 1077-2083).
**What:** The file works well: `vi: Partial<Messages>` falls back to English, `i18n:report` lists gaps, and `codes.test.ts` guarantees every rule code and event type has a sentence. But the key order has drifted (`nav.reports` sits in the middle of the `report.*` block), and translators edit a file with 1,000 lines of English in it. Keys are built dynamically (`error.${code}`, `eventType.${type}`, `stayStatus.${s}`) with `as MessageKey` casts, so dead-key detection would take a script.
**Direction:** Split into `i18n/en.ts` and `i18n/vi.ts`, grouped by namespace. Add an "unused keys" line to `i18n:report`. Low priority, and cheap once vi stabilizes.

### F15. Master vs own folio doubles the adapters and UI — low
**Where:** `api/folio.ts:103-109` (`masterPaymentInput`, `masterTransferInput`, `masterForfeitInput` + 3 extra server fns), `ui/master-folio.tsx` vs `ui/folio.tsx`, `e2e/journeys/support.ts:25` vs `e2e/support/desk.ts:12` (a duplicated `t()`).
**What:** The domain already takes a `FolioRef` union. The wire splits it into parallel functions on purpose (the comment explains that "neither" should not be expressible), and the UI follows the split. A `z.union` on the wire would give the same guarantee, as `moveInput` already shows at `api/folio.ts:48-55`.
**Direction:** Use `ref: z.union([{stayId},{bookingId}])` on the three money commands and drop the master twins. Share the payment form between both panels.

## 4. Strengths

- **The write path is excellent.** It is one function (`store/log.ts:232`), with a thunk-per-attempt retry, idempotency lookup before rules, atomic batch or refuse (no silent degraded mode), and command vs stream unique-violation classification. It is well tested, including interleavings in `guard.test.ts`.
- **The architecture is real, not aspirational.** `Hotel` methods are the commands, capability checks live in the domain (`ctx.must`), and the drizzle boundary is lint-enforced. Tier (a) (`fold*` + `decide`) vs tier (b) (`xRules` + row helpers in `setup.ts` / `rooms.ts`) is readable from the names alone.
- **The tests are a genuine asset.** There are 517 tests running in 10 s against the real SQLite store (no fakes), and scenario names read like the rules ("refuses a check-in into a room that is out of order"). A small `given.*` testkit plus counting ids and a fixed clock keep them readable. e2e adds cross-cutting guards (`no-get-forms`, `no-pii-in-url`, `no-silent-block`) that turn past incidents into permanent checks.
- **Refusals are handled consistently end to end.** `RuleError{code, detail}` → `command()` → `useCommand` → `CommandError` translates, with a quiet variant for `nothingToChange`. `codes.test.ts` makes it impossible to ship a code with no sentence.
- **PII discipline is structural.** Events carry ids only, names resolve at read time, rebuild excludes the PII tables, and redaction is by column name. All of it has tests.
- **Comments explain *why*.** Most non-obvious rules have their reason next to them, linked to a decision id. The problem is upkeep (F9), not absence.
