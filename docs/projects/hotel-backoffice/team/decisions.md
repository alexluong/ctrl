### D-6 · Setup/configuration is its own scope with a third persona; no ezFolio admin login
Accepted · 2026-09-23 · Alex (via solex-explore). Context: ezFolio item masters are permission-blocked; catalogue has rotted (duplicate/garbage items) precisely because pricing is admin-only and invisible to the people who price. Decision: stop chasing an admin login. Personas = **manager** (reads) · **receptionist** (runs the day) · **setup/admin** (defines rooms/types/prices, catalogues, tax/service %, booking rules, hotel identity; rarely used; realistically the owner). Consequences: product adds a Setup bounded context designed from a checklist, not from ezFolio's screens; whoever prices things can see and edit the catalogue.

### D-7 · Hotel day is a business date with a configurable roll; nights derive from timestamps + rules
Accepted · 2026-09-23 · Alex. Context: ezFolio rolls at 23:59 (calendar day); late arrivals (e.g. 01:00) should count as the prior night. Decision: `BookingRules` in Setup holds `businessDayStart` (default 02:00, Alex's recollection — client sets), `checkInTime` 14:00, `checkOutTime` 12:00, early/late thresholds. A night = one business date; nights charged = business dates in [arrival_bd, departure_bd) derived from actual timestamps + rules; reserved dates are the plan; early/late/extra-night are events + catalogue surcharges. Room charge posts at the roll. "Revenue today" = posted charges; occupancy × rate = forecast. Consequences: closes §10 #1 / "day boundary"; product models BookingRules + business-date derivation; roll time is not a client question, just a default.

### D-8 · Storage: D1 for event log + projections, optimistic concurrency, no Durable Object, Hookdeck deferred
Accepted (de facto) · 2026-09-23 · Alex asked dev in-session for the ES skeleton; dev built exactly this shape and deployed it (`stack.md` §"The ES skeleton as built"). Alex can still override. Originally Proposed by solex-dev (desk exercise vs `product.md` §5–6). Context: product proposed a single-writer DO per hotel for Reservations + D1 projections. Dev: DO exists only inside workerd → puts Cloudflare back in the dev loop (violates D-3 amendment); two storage systems; testing an aggregate = testing a DO. Decision (proposed): one `events(stream_id, version, type, payload, occurred_at, actor)` table, `UNIQUE(stream_id, version)`, append-with-expected-version + retry; `availability:<hotel>` stream as the serialisation point; projections written in the **same D1 `batch()`** (atomic) — synchronous v1, no queue; rebuild = re-fold the table. Cloudflare Queues later only for slow/external consumers. Hookdeck: no role for the log; maybe OTA-webhook ingest later. Consequences if accepted: product drops the DO from §6; Hookdeck-retention Q closes as moot; the "event-store design WS" collapses into this. Product confirmed 2026-09-23: availability stream covers both invariants (per-room no overlap; per-type per-night count ≤ rooms in service), on one condition — **every supply- or demand-changing command versions `availability:<hotel>` in the same batch**: RoomAssigned/RoomChanged/StayDatesChanged, StayCheckedIn-with-assignment, RoomTakenOutOfOrder/ReturnedToService, Room retire/type change (Setup), OverbookingOverridden. Miss one → stale supply. Product drops DO from §6 in v1. Built: `events(seq, stream_id, version, …)` + same-batch projections + replay; first aggregate Room; system console at `/system`.

### D-9 · Multi-tenant by design, one tenant in practice
Accepted · 2026-09-23 · Alex (product session; flipped by architect — Alex's call). Context: client is one property, but Alex wants a platform shape. Decision: everything hangs off a `Hotel` — rooms, bookings, folios, catalogue, rules, users; every event stream and projection keyed by hotel (`availability:<hotel>` per D-8 already is). No cross-hotel data in v1 (no shared guests/companies, no cross-hotel reports). Setup context = onboarding a hotel. **Not in v1**: self-signup, billing/plans, super-admin console. Tenant creation/seeding via an admin SDK or script, not a polished UI — fine to leave un-exposed. Consequences: product §1 framing updated; `hotelId` on every aggregate/table; users scoped to one hotel (multi-hotel users later).

### D-10 · Event payload versioning
Proposed · 2026-09-23 · architect (dev raised it). Context: payloads are unversioned JSON; a later field rename needs an upcaster. Decision (proposed): add `schema_version INTEGER NOT NULL DEFAULT 1` on `events`; event types are never renamed (add a new type instead); payload shape changes bump `schema_version` and register an upcaster `(type, from) → payload` applied at load, before fold; projections/rebuild always see the latest shape. Cheap now, painful retrofitted. Needs: Alex nod; dev to add the column before Booking.

### D-11 · Auth for SoLex
Proposed · 2026-09-23 · architect (dev raised it). Context: room board is public on staging; console = one shared token. `docs/stack.md` auth stance (2026-07-10, Go-era): services touch only an auth interface; production mode = standard OIDC, IdP swappable by config. Roles per D-6 personas, hotel-scoped per D-9. Console stays token-gated until users exist. Needs: Alex picks the IdP + whether staging gets auth before Booking.

### D-10 · Event naming, envelope, and date types
Proposed · 2026-09-23 · Alex (product session). Naming: `<aggregate>.<past_tense_verb>`, lowercase dotted, snake_case (`booking.created`, `stay.room_assigned`). Envelope on every event: `id` (ulid), `hotelId`, `stream`, `version` (UNIQUE per D-8), `type`, `schemaVersion`, `payload`, `occurredAt` (Instant, UTC), `businessDate` (LocalDate, stored at write per D-7), `actor` (user | system job), `correlationId`, `causationId?`, `commandId?` (idempotency). Date types: `LocalDate` for nights/business dates, `Instant` for moments; `HotelProfile.timeZone` is the only zone. Model uses American English. Consequences: dev's `events` table gains these columns; product §6 rewritten as TS types.

### D-11 · Booking v1 scope: minimal envelope, no OTA/commission logic, deposit lives on the folio
Proposed · 2026-09-23 · Alex (product session). Booking = `kind`, `party {companyId?, contactName, phone?}`, `sourceId?` (Setup-defined BookingSource list, lookup only), `arrive/depart`, `requests[]`, `notes`, `status`. Two-level Booking → RoomStay kept; individual = one stay assigned at creation. Deferred: OTA support (commission, gross/net, sync, external ref), sales rep, group label/color, merge-into-group. Deposit = folio payment of kind `deposit`, not a Booking field. Consequences: §10 #5 (OTA commission basis) and #8 (group billing default) move to Later; Setup gains `BookingSource`.

### D-12 · Naming Booking/Stay; Stay v1 shape; room-move and extend assumptions
Proposed · 2026-09-23 · Alex (product session). Terms: **Booking** (not Reservation) and **Stay** (not RoomStay); streams `booking:*`, `stay:*`. Stay = roomType/bedType, `roomId?` (late-bound), arrive/depart (plan), per-night rates, adults/children, guests, routing (group only), status `booked|checkedIn|checkedOut|cancelled|noShow`, actual check-in/out instants. Dropped ezFolio flags foc/isNet/locked. Assumptions (business calls, adjustable): room move mid-stay = same stay, no reprice, warn on type change; extend = same stay, new nights from rate table, editable before posting. Consequences: product §6 Stay in TS; `RoomStay` renamed everywhere.

### D-13 · The night is the unit: Stay = nights[] each with room + rate; room move never splits a Stay
Proposed · 2026-09-23 · Alex (product session). Stay holds `nights: {date, roomId?, rate, posted}[]`; arrive/depart derived. Room move rewrites roomId on unposted nights from a date; Stay (folio, guests, status) stays one thing because it is one guest visit. Availability = no two stays share `(roomId, date)`; per-type count per night. Overbooking = warn + explicit override (assumed, high occupancy). Housekeeping = clean/dirty only in v1; inspected later. Consequences: tape chart draws nights, a moved stay shows as two bars; posted nights immutable; `stay.room_assigned/room_changed` carry a fromDate.

### D-14 · Money v1: own + master folios, Setup-defined charge categories, receivable per folio w/o due date, no discount approvals
Proposed · 2026-09-23 · Alex (product session). Folio per Stay + master per group Booking; charge posted against a stay, routed by category. Charge categories = Setup-defined list seeded with ezFolio's (minus telephone), `room` reserved for the system. Payment methods cash | bankTransfer | card (word only, no card data); kinds deposit | settlement | refund. Deposit lives on the folio. Receivable grain = folio, debtor = Company, **no due date** (overdue = age). Discount approval workflow **skipped in v1** → ticket. Tax/VAT lines → later. Consequences: §10 #3-ish items close; Setup gains `ChargeCategory`; requirements' "manager approves discounts" deferred.

### D-15 · Generic Ledger context (double-entry) under Billing and Expenses; Setup is upstream reference data
Proposed · 2026-09-23 · Alex (product session; Alex's suggestion). Ledger = `Account {kind folio|receivable|cash|bank|revenue|expense}` + immutable `Entry {lines Σ=0}`; undo = reversal. Folio and Receivable become Billing *projections + commands* over Ledger accounts, not aggregates; Expense posts to Ledger. Reception sees hotel vocabulary only. Contexts: Setup → {Reservations, Rooms, Billing→Ledger, Guests, Expenses→Ledger}; dependencies one-way; Setup read by lookup at command time, reacted to only for supply changes. Consequences: one balance rule and money log; cash/revenue/AR/P&L are one query; dev models `accounts`, `entries`, `entry_lines`.

### D-16 · Users per person, two roles, three apps
Proposed · 2026-09-23 · Alex (product session). Individual user accounts scoped to a hotel; multiple receptionists share one role; actor on every event. Product = apps (Front Desk, Back Office, Setup); role = app access: `receptionist` → Front Desk (+ Back Office receivables/expenses, assumed), `owner` → all. Authz is **capability-based, checked per command**; roles are named capability bundles; v1 ships two fixed bundles (`receptionist`, `owner`), custom roles later; void/refund/write-off/setup/users in `owner` by default; reports owner-only. Admin SDK outside the apps. Consequences: auth model = user → hotel → role → apps; §2 rewritten; D-6 "setup persona" becomes the Setup app for the owner.
