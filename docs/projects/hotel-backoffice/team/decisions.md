### D-8 · Storage: D1 for event log + projections, optimistic concurrency, no Durable Object, Hookdeck deferred
Accepted (de facto) · 2026-09-23 · Alex asked dev in-session for the ES skeleton; dev built exactly this shape and deployed it (`stack.md` §"The ES skeleton as built"). Alex can still override. Originally Proposed by solex-dev (desk exercise vs `product.md` §5–6). Context: product proposed a single-writer DO per hotel for Reservations + D1 projections. Dev: DO exists only inside workerd → puts Cloudflare back in the dev loop (violates D-3 amendment); two storage systems; testing an aggregate = testing a DO. Decision (proposed): one `events(stream_id, version, type, payload, occurred_at, actor)` table, `UNIQUE(stream_id, version)`, append-with-expected-version + retry; `availability:<hotel>` stream as the serialisation point; projections written in the **same D1 `batch()`** (atomic) — synchronous v1, no queue; rebuild = re-fold the table. Cloudflare Queues later only for slow/external consumers. Hookdeck: no role for the log; maybe OTA-webhook ingest later. Consequences if accepted: product drops the DO from §6; Hookdeck-retention Q closes as moot; the "event-store design WS" collapses into this. Product confirmed 2026-09-23: availability stream covers both invariants (per-room no overlap; per-type per-night count ≤ rooms in service), on one condition — **every supply- or demand-changing command versions `availability:<hotel>` in the same batch**: RoomAssigned/RoomChanged/StayDatesChanged, StayCheckedIn-with-assignment, RoomTakenOutOfOrder/ReturnedToService, Room retire/type change (Setup), OverbookingOverridden. Miss one → stale supply. Product drops DO from §6 in v1. Built: `events(seq, stream_id, version, …)` + same-batch projections + replay; first aggregate Room; system console at `/system`. **Stream id shape (architect, 2026-09-23):** `<hotel>/<kind>:<id>` always, hotel first (D-9); the availability stream is therefore `<hotel>/availability:all` (e.g. `solex/availability:all`), not the literal `availability:<hotel>` of §12 — same thing, hotel not encoded twice. Cross-stream atomic append (`appendAcross`/`handleAcross`, e2a745e): one `commandId` on the first event of the whole command, shared `correlationId`, `prepare` re-run per attempt across all streams. **Clarification 2026-09-23 (architect, from Alex walkthrough):** (i) reads never fold — screens `SELECT` projection tables; fold happens only at command time over one small stream; `availability:<hotel>` is a version counter, not state — decide reads the `room_calendar` projection (same-batch, so consistent) under that guard; snapshots only if a real stream ever gets slow. (ii) **one user intent = one command = one D1 `batch()`**; a command may version several streams (check-in = `stay.checked_in` + room row/event). (iii) **Reactions** (§10 policies like `stay.checked_out → room.marked_dirty`) run inline in the command's batch, once; they are **not** re-run on replay. **Projectors** are re-run on replay. Async cursor consumers (`WHERE seq > last_seq`) only when leaving the DB (email, OTA). (iv) A command never trusts UI-loaded data; it reloads and redecides; optional `expectedVersion` from the UI for "changed since you looked".

### D-12 · Event naming, envelope, and date types
Accepted · 2026-09-23 · Alex (product session; flipped by architect). Naming: `<aggregate>.<past_tense_verb>`, lowercase dotted, snake_case (`booking.created`, `stay.room_assigned`). Envelope on every event: `id` (ulid), `hotelId`, `stream`, `version` (UNIQUE per D-8), `type`, `schemaVersion`, `payload`, `occurredAt` (Instant, UTC), `businessDate` (LocalDate, stored at write per D-7), `actor` (user | system job), `correlationId`, `causationId?`, `commandId?` (idempotency). Date types: `LocalDate` for nights/business dates, `Instant` for moments; `HotelProfile.timeZone` is the only zone. Model uses American English. Upcasting (architect, from dev's ask): types never renamed (add a new type); payload shape change bumps `schemaVersion` + registers an upcaster `(type, from) → payload` applied at load, before fold. Consequences: dev's `events` table gains these columns; product §6 rewritten as TS types. **Clarification 2026-09-23 (architect, Alex Q on idempotency):** concurrency ≠ idempotency. Concurrency = `UNIQUE(stream_id, version)` + the D-8 availability-stream rule (two desks, one wins, loser re-reads and sees the clash). Idempotency = client-minted `commandId` (ulid at click time, reused on retry) + `UNIQUE` index on `events.command_id`; a duplicate batch hits it and `handleCommand` returns the original result as success. Decide should also no-op when the intent already holds (zero events → nothing written). Money commands (`folio.post_charge`, `payment.*`) MUST be idempotent by `commandId`; others get it for free. **Amendment 2026-09-23 (architect under D-21, dev built ca19a48):** (a) `actor` is stored as one indexed text column `user:<id>` | `system:<job>`, not a JSON union — same two variants, lossless, keeps actor lookup/filter simple; product aligns §6. (b) Upcaster registry `(type@from) → payload` applied on read; on an unregistered gap the **fold/command path fails loud** (`readStream` used by `handleCommand` throws) — a stale-shaped payload folded into a money aggregate is silently wrong state; **display paths** (console event browser, history tabs) stay tolerant and mark the row as un-upcast. (c) `commandId` on the first event of a command; siblings share `correlationId`; duplicate `commandId` returns the original events as success; the browser keeps the minted id until *any* answer arrives. (d) `businessDate` computed in the hotel zone, `Asia/Ho_Chi_Minh` hardcoded with `TODO(D-7)` until HotelProfile exists. (e) Envelope migration was hand-written (drizzle-kit's `ADD COLUMN NOT NULL` only works on an empty table): rebuild + backfill `legacy-<seq>` ids, applied to populated D1.

### D-22 · Two tiers: event-sourced core, event-notified reference data
Accepted · 2026-09-23 · Alex (in architect session): "we can be event-based, so room changes should also have events but we don't need event source for it… we shouldn't be dogmatic about EVERYTHING." Context: dev's skeleton made Room the first ES aggregate; product's model has ~40 commands; ES ceremony (payload + schemaVersion + upcaster + projector per change) is only worth it where "who did what when" and replay matter. Decision: **(a) Event-sourced** — Booking, Stay, Ledger (folio/receivable are projections over Ledger): the `events` log is the source of truth, state = fold, invariants via `UNIQUE(stream_id, version)` + the `availability:<hotel>` stream (D-8). **(b) Event-notified** — Room, RoomType, RateType, ChargeCategory, Company, Guest/Contact, User, HotelProfile and other Setup data: a mutable CRUD table is the source of truth; every write still appends an event (`room.updated`, `room.set_out_of_order`, `guest.erased`…) to the **same** log, in the same batch, D-12 envelope, for history tabs, projections, later async consumers — but nothing folds it and there is no version guard beyond the row. Rule of thumb: if the answer to "would we ever replay this to rebuild state?" is no, it's tier (b). Consequences: dev flips Room from ES aggregate to CRUD + events (small; keeps the log-writing path); §11 command catalogue stays valid, each command is tagged with its tier by product; PII rule D-20 unchanged (tier b tables are where PII lives); `rebuildProjections` replays tier (a) streams and tier (b) events alike, so projections can still be derived from both. **Addendum 2026-09-23 (architect, dev's questions):** a tier (b) table may be owned by a library (Better Auth's `user`); our command path never writes it directly — creation goes through the library, our command appends the `user.*` event alongside. Staff membership/roles = tier (b) too (`hotel_staff(user_id, hotel_id, role, active)` + `staff.role_changed`…): history is in the events, nothing needs a fold. **Staging log**: wiped once at the Room flip rather than carrying `RoomDefined`-era names next to `room.*` forever (D-11 declared staging throwaway until login; login landed same day; D-12 "types never renamed" applies from the envelope migration onwards, no permanent exception). Alex 2026-09-23 (architect session): "i'll defer to you; staging is indeed throwaway data, at least at the moment" → wipe approved, Room flip greenlit.

### D-24 · Domain SDK: one `Hotel` application object, screens and tests call the same methods
Accepted · 2026-09-23 · Alex (architect session): "I want the domain layer to be very direct so we can have a very clear test suite… some level of SDK-like usage… from the API POV it will just interact with the domain as such." Decision: the application layer is a typed object `Hotel { rooms, bookings, stays, folios, … }` whose methods **are** the commands (`hotel.stays.checkIn({stayId, guests})`), each = load → decide → append through a `Store` interface + a `Clock`. Two `Store` implementations: `SqliteStore` (local file / D1, the existing store.ts) and `MemoryStore` (tests). Server functions are thin adapters: zod parse → `requireUser()` → `hotel.<agg>.<cmd>(input)` → map rule error to `{ok:false, code}`; **no domain logic in a server fn**. Read side exposed the same way (`hotel.calendar.on(date, roomId)`, `hotel.events.of(stream)`) over projection tables. Test layers: (1) `domain/*` fold/decide table tests (pure, sync); (2) **main suite** = scenarios against `hotel()` with `MemoryStore` + fixed clock + `given.*` fixture builders (`given.checkedInStay(...)`), reads like the rule: "cannot check in to an OOO room", "two desks race for the last room, one wins", "early check-out frees remaining nights"; (3) infra: SQLite atomicity / UNIQUE guard / replay equality (existing). The race and replay scenarios run against **both** stores via the shared interface. Rule-failure assertion helper `rejects.rule('stay.roomOutOfOrder')`. Consequences: dev refactors `booking/commands.ts` + `rooms/commands.ts` into `Hotel` before slice-1 screens; `handleAcross`/`recordChange` become `Store` internals; the testkit (`hotel()`, `given`) lives in the repo, not a separate package; product.md §11 command names map 1:1 to SDK methods. **Amendment 2026-09-23 (dev proposed, architect accepted):** no hand-written `MemoryStore`. Both bindings are the same `SqliteStore` code: D1/libsql file in prod, `@libsql/client` `:memory:` + migrations in tests (ms). Reason: commands don't only append — they run `roomIsFree`, read rows, batch upserts; a second implementation of those queries would make the scenario suite pass where SQL breaks. Tests get real UNIQUE + real batch atomicity. Store-interface leakage is caught by a lint boundary instead: drizzle imported only under `store/` (biome `noRestrictedImports`). Shape as built: every command takes one object with optional `commandId`, returns created ids or void, fails by throwing a shared `RuleError {code}`; actor per `hotel()` instance; reads (`rooms.list/find`, `bookings.*`, `stays.*`, `calendar.on/roomFree/grid`, `events.ofStay/ofRoom/ofBooking`) on the same object. `hotel(deps)` is strict in prod (store required); the testkit's `testHotel(partial)` supplies `:memory:` store, fixed clock, counter ids.

### D-25 · Nightly room-charge posting fires from cron and lazily, idempotent per (stay, night)
Accepted · 2026-09-23 · architect under D-21 (proposed to Alex in-session, no objection). Context: §10 row 1 / D-7 say the room charge posts "at the roll" (`businessDayStart`, default 02:00) but not what fires it. Decision: `PostNightlyRoomCharges` is a system command (actor `system:night_roll`) keyed by `(stayId, businessDate)`, idempotent — posting a night twice is a no-op. It is triggered **both** by a Cloudflare Cron Trigger at the roll (production) and **lazily** on the first request after the roll (any request that reads today's business date checks `lastRolledDate < today` and posts what's missing, in-batch, before answering). Local dev = lazy only. Rationale: cron alone silently loses a night's revenue when it misses; lazy alone leaves the dashboard stale on a quiet night. Consequences: `HotelProfile.businessDayStart` changes are owner-only and **refused while any night of the current business date is unposted** (moving the roll mid-day re-labels nights); check-in posts tonight's night immediately (§7) through the same idempotent command, so the roll can't double-post it.
