### D-6 · Setup/configuration is its own scope with a third persona; no ezFolio admin login
Accepted · 2026-09-23 · Alex (via solex-explore). Context: ezFolio item masters are permission-blocked; catalogue has rotted (duplicate/garbage items) precisely because pricing is admin-only and invisible to the people who price. Decision: stop chasing an admin login. Personas = **manager** (reads) · **receptionist** (runs the day) · **setup/admin** (defines rooms/types/prices, catalogues, tax/service %, booking rules, hotel identity; rarely used; realistically the owner). Consequences: product adds a Setup bounded context designed from a checklist, not from ezFolio's screens; whoever prices things can see and edit the catalogue.

### D-7 · Hotel day is a business date with a configurable roll; nights derive from timestamps + rules
Accepted · 2026-09-23 · Alex. Context: ezFolio rolls at 23:59 (calendar day); late arrivals (e.g. 01:00) should count as the prior night. Decision: `BookingRules` in Setup holds `businessDayStart` (default 02:00, Alex's recollection — client sets), `checkInTime` 14:00, `checkOutTime` 12:00, early/late thresholds. A night = one business date; nights charged = business dates in [arrival_bd, departure_bd) derived from actual timestamps + rules; reserved dates are the plan; early/late/extra-night are events + catalogue surcharges. Room charge posts at the roll. "Revenue today" = posted charges; occupancy × rate = forecast. Consequences: closes §10 #1 / "day boundary"; product models BookingRules + business-date derivation; roll time is not a client question, just a default.

### D-8 · Storage: D1 for event log + projections, optimistic concurrency, no Durable Object, Hookdeck deferred
Accepted (de facto) · 2026-09-23 · Alex asked dev in-session for the ES skeleton; dev built exactly this shape and deployed it (`stack.md` §"The ES skeleton as built"). Alex can still override. Originally Proposed by solex-dev (desk exercise vs `product.md` §5–6). Context: product proposed a single-writer DO per hotel for Reservations + D1 projections. Dev: DO exists only inside workerd → puts Cloudflare back in the dev loop (violates D-3 amendment); two storage systems; testing an aggregate = testing a DO. Decision (proposed): one `events(stream_id, version, type, payload, occurred_at, actor)` table, `UNIQUE(stream_id, version)`, append-with-expected-version + retry; `availability:<hotel>` stream as the serialisation point; projections written in the **same D1 `batch()`** (atomic) — synchronous v1, no queue; rebuild = re-fold the table. Cloudflare Queues later only for slow/external consumers. Hookdeck: no role for the log; maybe OTA-webhook ingest later. Consequences if accepted: product drops the DO from §6; Hookdeck-retention Q closes as moot; the "event-store design WS" collapses into this. Product confirmed 2026-09-23: availability stream covers both invariants (per-room no overlap; per-type per-night count ≤ rooms in service), on one condition — **every supply- or demand-changing command versions `availability:<hotel>` in the same batch**: RoomAssigned/RoomChanged/StayDatesChanged, StayCheckedIn-with-assignment, RoomTakenOutOfOrder/ReturnedToService, Room retire/type change (Setup), OverbookingOverridden. Miss one → stale supply. Product drops DO from §6 in v1. Built: `events(seq, stream_id, version, …)` + same-batch projections + replay; first aggregate Room; system console at `/system`.

### D-12 · Event naming, envelope, and date types
Accepted · 2026-09-23 · Alex (product session; flipped by architect). Naming: `<aggregate>.<past_tense_verb>`, lowercase dotted, snake_case (`booking.created`, `stay.room_assigned`). Envelope on every event: `id` (ulid), `hotelId`, `stream`, `version` (UNIQUE per D-8), `type`, `schemaVersion`, `payload`, `occurredAt` (Instant, UTC), `businessDate` (LocalDate, stored at write per D-7), `actor` (user | system job), `correlationId`, `causationId?`, `commandId?` (idempotency). Date types: `LocalDate` for nights/business dates, `Instant` for moments; `HotelProfile.timeZone` is the only zone. Model uses American English. Upcasting (architect, from dev's ask): types never renamed (add a new type); payload shape change bumps `schemaVersion` + registers an upcaster `(type, from) → payload` applied at load, before fold. Consequences: dev's `events` table gains these columns; product §6 rewritten as TS types.

### D-14 · Naming Booking/Stay; Stay v1 shape; room-move and extend assumptions
Accepted · 2026-09-23 · Alex (product session; flipped by architect). Terms: **Booking** (not Reservation) and **Stay** (not RoomStay); streams `booking:*`, `stay:*`. Stay = roomType/bedType, `roomId?` (late-bound), arrive/depart (plan), per-night rates, adults/children, guests, routing (group only), status `booked|checkedIn|checkedOut|cancelled|noShow`, actual check-in/out instants. Dropped ezFolio flags foc/isNet/locked. Assumptions (business calls, adjustable): room move mid-stay = same stay, no reprice, warn on type change; extend = same stay, new nights from rate table, editable before posting. Consequences: product §6 Stay in TS; `RoomStay` renamed everywhere.

### D-15 · The night is the unit: Stay = nights[] each with room + rate; room move never splits a Stay
Accepted · 2026-09-23 · Alex (product session; flipped by architect). Stay holds `nights: {date, roomId?, rate, posted}[]`; arrive/depart derived. Room move rewrites roomId on unposted nights from a date; Stay (folio, guests, status) stays one thing because it is one guest visit. Availability = no two stays share `(roomId, date)`; per-type count per night. Overbooking = warn + explicit override (assumed, high occupancy). Housekeeping = clean/dirty only in v1; inspected later. Consequences: tape chart draws nights, a moved stay shows as two bars; posted nights immutable; `stay.room_assigned/room_changed` carry a fromDate.

### D-22 · Two tiers: event-sourced core, event-notified reference data
Accepted · 2026-09-23 · Alex (in architect session): "we can be event-based, so room changes should also have events but we don't need event source for it… we shouldn't be dogmatic about EVERYTHING." Context: dev's skeleton made Room the first ES aggregate; product's model has ~40 commands; ES ceremony (payload + schemaVersion + upcaster + projector per change) is only worth it where "who did what when" and replay matter. Decision: **(a) Event-sourced** — Booking, Stay, Ledger (folio/receivable are projections over Ledger): the `events` log is the source of truth, state = fold, invariants via `UNIQUE(stream_id, version)` + the `availability:<hotel>` stream (D-8). **(b) Event-notified** — Room, RoomType, RateType, ChargeCategory, Company, Guest/Contact, User, HotelProfile and other Setup data: a mutable CRUD table is the source of truth; every write still appends an event (`room.updated`, `room.set_out_of_order`, `guest.erased`…) to the **same** log, in the same batch, D-12 envelope, for history tabs, projections, later async consumers — but nothing folds it and there is no version guard beyond the row. Rule of thumb: if the answer to "would we ever replay this to rebuild state?" is no, it's tier (b). Consequences: dev flips Room from ES aggregate to CRUD + events (small; keeps the log-writing path); §11 command catalogue stays valid, each command is tagged with its tier by product; PII rule D-20 unchanged (tier b tables are where PII lives); `rebuildProjections` replays tier (a) streams and tier (b) events alike, so projections can still be derived from both.
